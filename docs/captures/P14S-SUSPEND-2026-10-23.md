# P14s Gen 1 + ORICO AAGM2-U4: suspend-to-idle on the Alpine Ridge firmware CM

Status: 2026-10-23. Licence: GPL-2.0-only, like the rest of this repository.

The ThinkPad P14s Gen 1 (Intel JHL6240 Alpine Ridge LP, firmware connection manager)
with the ORICO AAGM2-U4 USB4 NVMe enclosure (ASMedia ASM2464PD), BIOS settings as run R1
of [P14S-ORICO-2026-10-15.md](P14S-ORICO-2026-10-15.md) (Thunderbolt BIOS Assist off,
pre-boot support off, security `user`, CSM boot), with one suspend-to-idle
(`rtcwake -m freeze -s 15`). The question was what the firmware CM does across a system
suspend, and whether the tunnel and the NVMe survive it.

Labels: **[obs]** seen in the capture (citation follows), **[inf]** implied but not
shown, **[spec]** from a specification or from the Linux client's source (behaviour
only). The answer is short: the enclosure was not on the Thunderbolt link when the
machine suspended, so this run says nothing about a tunnel across suspend (§2). It does
show the client's suspend and resume, the NHI registers across it, and a USB-mode device
on the controller's xHCI surviving it.

## 2. Tunnel and NVMe across the suspend

**There was neither [obs].** At the suspend the ORICO was a USB disk on the controller's
xHCI; `snap-6-approved/sys-bus-thunderbolt/` holds only the host router and the domain, and
`pci/nvme-with-device.txt` shows the enclosure's disk as `sda` (238.5 GB, model
`ASM246X`, transport `usb`); its only NVMe is the laptop's internal disk, present since
boot. So whether the firmware CM keeps a PCIe
tunnel across suspend-to-idle, and whether the NVMe behind it keeps its state, is not
answered by this run.

What the run does show about the controller:

- The USB disk on 2b:00.0 survived the suspend: no disconnect, no reset or
  re-enumeration of `usb 4-1` between `D:226.104` and the final unplug at `D:262.955`
  [obs]. So the Alpine Ridge chip, which carries both the xHCI and the USB-mode link, was
  not power-cycled as a whole during this s2idle [inf]; its Thunderbolt side was reset
  (§4.1).
- The firmware CM was answering at once after the resume: driver ready answered in
  4.5 ms with the values of every earlier bind, and every boot ACL read during the
  unplug and tail watches (17 reads, 258.6-355.2) succeeded in at most 40 ms
  (`watch/icm-probe.tsv`) [obs].

## 3. What the client sent at the suspend

[spec] Linux `icm.c`: for Alpine Ridge, `icm_suspend()` (the `suspend` callback, run from
`nhi_suspend()` in the device suspend phase) sends mailbox **0x05 "save devices"**
(`icm_fr_save_devices`) and then **0x07 "driver unloads"**; `nhi_suspend_noirq()`
stops the control channel; on resume `icm_complete()` marks every device router
unplugged, sends driver ready, and 500 ms later removes routers that were not
re-announced. No mailbox command is sent on resume.

[obs] The ring stop and restart (`D:226.552`, `D:243.006`) and the post-resume driver
ready (`T:244.084`) are in the capture, at the places the code puts them. The two
mailbox commands are not: `nhi_mailbox_cmd()` writes MMIO and logs nothing, and the
trace covers ring 0 only. The register they leave behind does not show them either (§4).
So 0x05 stays **[inf]** in `ICM-PROTOCOL.md` §2.3; the capture is consistent with it and
adds that its effect, for a domain with no device router, is nothing visible.

## 4. NHI registers before and after

All from the NHI BAR0 (0x39904 inbound mailbox command, 0x3990c outbound mailbox,
0x39944 firmware status) [obs] `M:*`, `W:*`:

| Point | OUTMAIL_CMD | INMAIL_CMD | FW_STS | Power |
|---|---|---|---|---|
| `M:1-initial` (power-on, before any bind) | `0x800003f0` | `0x00000000` | `0x800001a1` | D0 |
| `M:2-first-bind`, `M:3-after-rebind`, `M:4`-`M:6`, `W:164.140`-`W:226.054` | `0x800003f0` | `0x00000023` | `0x800001a1` | D0 |
| `M:2-unbound` | `0x800003f0` | `0x00000007` | `0x800001a1` | D0 |
| `W:231.456` (first sample after the resume) to `M:7-unplugged-again` | **`0x800003f5`** | **`0x00000000`** | `0x800001a1` | D0 |

- **OUTMAIL_CMD `0x800003f0` -> `0x800003f5`.** NHI runtime PM was off for the whole
  run (`power-control-changes.txt`: `power/control` was already `on`), so the NHI never
  runtime-suspended and the s2idle was its first D3 since power-on. The low nibble became
  5 across it and stayed 5. This is the rule already recorded from R1 (`ICM-PROTOCOL.md`
  R2: 5 once the NHI has entered D3, until device reset), now seen with system suspend
  as the D3 entry [obs]. That the NHI entered D3 during the s2idle is [inf]: the watch
  does not sample while the system is suspended, and Linux's PCI core puts a device in
  D3hot at system suspend [spec].
- **INMAIL_CMD `0x23` -> `0`.** If 0x05 and 0x07 were sent as the code says, the code
  field should have read `0x07` afterwards, as it did after the unbind (`M:2-unbound`).
  It read 0. This is not specific to system suspend: in R1 of 2026-10-15 the register
  also read 0 after the first runtime D3hot exit (R1-W:145.874) and after a D3cold exit
  (R1-W:236.047), and `0x07` after another D3hot exit (R1-W:218.049). So the code field
  after a D3 exit is not dependable [obs], for a reason not visible here (a function
  reset on some D3hot exits, or the firmware clearing it, [inf] either way). Linux never
  reads the field except to mask it out before writing a command, so this has no effect
  on the client.
- **FW_STS `0x800001a1`** at every point: the firmware stayed running, authenticated and
  in CM mode [obs].
- NHI config space: identical before and after except PCIe Device Status (0xca), `0x19`
  (correctable and unsupported-request errors detected, AUX power) -> `0x10` (AUX power
  only) [obs] `mmio/*-6-approved.config.txt`, `*-6s-after-suspend.config.txt`. Whether
  the error bits were cleared by a reset or by the OS is not visible [inf].
- TX ring 0 producer/consumer `0x00090009` -> `0x00010001`: the ring was restarted and
  has carried one frame since, the post-resume driver ready [obs].

### 4.1 Host router registers (debugfs)

`snap-<n>/debugfs-thunderbolt/0-0/`, read by the Linux client through the firmware CM
[obs]:

- **Lane adapters 1 and 2** (`port1/regs`, `port2/regs`) are byte-identical in
  `snap-2`, `snap-3`, `snap-4` (nothing plugged), `snap-6s-after-suspend` and `snap-7`,
  and differ in `snap-5-plugged` and `snap-6-approved`, which were taken after the ORICO
  had fallen back to USB but was still in the port: lane capability dword 1 (0x37)
  `0x1c14001c` instead of `0x1c18001c`, vendor dwords 0x42/0x43 `1` instead of `0`, 0x45
  bit 5 set, 0x4a non-zero. So before the suspend the Thunderbolt side of the port still
  showed something attached; after it, the lane adapters read exactly as with nothing
  plugged, while the same device stayed connected over USB.
- **Adapter 3 (the NHI / DMA port)**: vendor dwords 0x3f-0x43 held data from the
  client's DMA-port NVM read at bind (`0x00230000 0x04282806 0x502f3531 ...`) up to
  `snap-6-approved` and read 0 after the suspend.
- **Router**: dword 0x38 `0x80000001` (after the plug) -> `0x00000005`, 0x4a
  `0x74200200` -> `0x74200114`, and many dwords of the vendor capabilities with ids 6, 7
  and 9 changed (not decoded here); the TMU time dwords change as they always do.

Together with the inbound mailbox reading 0 (§4), this says the Thunderbolt side of the
controller (host router, its adapters, the NHI mailbox) came out of the s2idle in a
reset state, while the controller's xHCI kept its USB device and the firmware CM stayed
running and answered at once [inf: a CIO/router reset by the firmware or the platform
during s2idle, rather than a power cycle of the whole chip, which would have dropped the
USB device; which one is not visible]. The 2026-10-14 runtime suspends of the NHI, with
the dock tunnelled, kept the tunnel (`ICM-PROTOCOL.md` §6.5); whether an s2idle also
keeps it, given this reset, is exactly what a capture with a tunnel must show (§8).

## 7. What the Alpine Ridge profile should do across suspend-to-idle

(Superseded by §10, the 07:45 run with a tunnel: the model now implements R34. What
follows is the decision taken from this first run alone.)

Decision: **no model change** from this capture.

- The client's s2idle path on Alpine Ridge is the runtime-suspend path plus mailbox 0x05:
  0x05, 0x07, rings stopped, NHI D3hot, then D0, rings restarted, driver ready, a 500 ms
  rescan [spec]. The model already does each step as captured: 0x05 completes without
  error (R3), 0x07 stops events and keeps tunnels and approvals (R3, §2.3), PMCSR D3
  makes the outbound mailbox `0x800003f5` (R2, seen again here, §4), and driver ready
  re-announces every attached approved device with approved = 1 (§6.5 of
  `ICM-PROTOCOL.md`, observed after runtime suspend). Under QEMU an s2idle involves no
  machine reset, so tunnels and endpoints simply stay up, which is also what the
  runtime-suspend capture shows for the real firmware.
- The inbound command field reading 0 after a D3 exit is not modelled: the captures show
  both 0 and the last code, and the client never depends on it (§4).
- The open question, the tunnel across s2idle on the real firmware, is not answered.
  Runtime suspend kept the tunnel (§6.5 of `ICM-PROTOCOL.md`), which is what the model
  does; but this s2idle reset the host router's adapters (§4.1), which a tunnel might not
  survive. A model change either way would be a guess, so the model stays as it is until
  a capture with a tunnel (§8).
- The router-side reset itself is not modelled either: with no device attached, as here,
  it is invisible to the client (driver ready and every later answer were as before).

## 8. S3 (deep) still needs its own capture

(Captured: §9 without a tunnel, §10 with one.)

Yes. The P14s offers it (`system/power-state-before-suspend.txt`: `freeze mem disk`,
`s2idle [deep]`, so `deep` is the default and the capture's `rtcwake -m freeze` chose
s2idle explicitly). S3 differs where it matters [inf]: the platform removes power from
the controller and the BIOS runs again on resume, so the firmware CM restarts, and
"save devices" (0x05) exists precisely so that the firmware can bring back devices
across that [spec: `icm.c` "Ask ICM to save devices to ACL when suspending"]. The
model's current S3 behaviour on `tb3-alpine-ridge` (GUEST-EXITS.md, "S3 and the PCIe
tunnel": tunnel down at the wakeup reset, router re-announced unapproved, NVMe needs a
new authorisation) is not backed by any capture, and the link-retrain work (owner
decision 2026-10-22, `ARCHITECTURE.md` §4.4 on that branch) settles S3 for the software
CM only.

Recommended next captures (owner):

1. **S3 with a tunnel**: Assist off, **pre-boot on** (the R2 cell: tunnel and NVMe at
   boot, no approve window to miss), ORICO attached at power-on,
   `sudo bash capture-linux.sh --label orico-s3 --watch-mmio 1 --suspend-deep`, with
   `thunderbolt.dyndbg=+p` spelled correctly. Look for: device connected after resume
   with approved = 1 or 0, PCIe link down/up on 04:01.0, the NVMe kept or re-enumerated
   (`lsblk` after resume, `nvme` lines in dmesg), OUTMAIL and FW_STS after resume.
2. **s2idle with a tunnel**: the same, with `--suspend`: does the tunnel survive the
   router reset of §4.1, is the device re-announced approved, is the NVMe kept?
3. Optionally the same two with the CalDigit TS3 Plus (a Thunderbolt 3 device, which
   does not fall back to USB), so the result does not depend on the ASM2464.

The model change, if S3 shows the firmware re-approving saved devices, would be in the
ICM's handling of the machine's wakeup reset and belongs after the link-retrain branch
merges (it touches `usb4-fabric.c`).

### What the owner must redo

The cause both times was the setting, not the tool: with pre-boot off the ORICO is a
USB disk from boot, and after a replug it must be approved within about 9 s. Do this:

1. BIOS (F1): Config > Thunderbolt 3: **Support in Pre Boot Environment > Thunderbolt
   device: Enabled**, BIOS Assist Mode: Disabled (the R2 cell). ORICO attached before
   power-on.
2. Kernel line: `thunderbolt.dyndbg=+p modprobe.blacklist=thunderbolt,typec,typec_ucsi,ucsi_acpi trace_buf_size=64M`
   (check the spelling `dyndbg`; the script now warns).
3. Boot, then let boltd store the ORICO so that it approves it after the replug: with
   the ORICO on Thunderbolt (`boltctl list` shows it), run
   `sudo boltctl enroll --policy auto 00279170-8e60-4c17-ffff-ffffffffffff`.
4. Run `sudo bash capture-linux.sh --label orico-preboot-suspend-s3 --watch-mmio 1 --suspend --suspend-deep`.
   At the plug prompt press Enter as soon as the enclosure is plugged, and answer `y`
   if asked to authorise it. Before answering the suspend questions, check that
   `lsblk` lists the enclosure as an `nvme` disk (not `sda`).

### 10.2 What the firmware CM did to the tunnel

- **The tunnel and the NVMe survived both suspends [obs].** No pciehp Link Down / Card
  not present on 04:01.0 between the approve and the final unplug; no PCI
  re-enumeration of 06:00.0-08:00.0 (no "configuration invalid", no "enabling device"
  after 144.1); the same `nvme0`/`nvme0n1` throughout (`pci/nvme-after-suspend.txt`,
  `pci/nvme-after-s3.txt`: `SKHynix_HFS256GDE9X081N`, transport `nvme`); `0-1` stays
  `authorized` = 1 (`snap-6s-after-suspend`, `snap-6m-after-s3`), no "device
  disconnected" and no new authorisation. The nvme driver re-initialised its queues on
  each resume, as it does for any NVMe across system sleep.
- **After S3 the PCIe tunnel was up before the OS's Thunderbolt driver spoke to the
  firmware.** The controller lost power in S3 (xHCI), yet the NVMe answered at dmesg
  227.696, about 0.6 s before driver ready (trace 228.366, dmesg about 228.29). So the
  firmware (BIOS and ICM on resume) re-established the tunnel to the device it had
  saved, by itself [obs for the order; that this is what mailbox 0x05 "save devices"
  arranges is inf]. After s2idle likewise (`S3b-D:205.246` before driver ready).
- **Re-announcement**: at the post-resume driver ready the firmware announced the
  ORICO as **approved** with **connection id 0** and **boot clear**, after holding the
  host-router polls 580 ms as at a bind (§6.2). Before the suspends the ids were 1, 2,
  3 and boot was set. So both s2idle and S3 restart the firmware CM's connection
  numbering and clear the pre-boot mark, and both keep the approval [obs]. Linux keeps
  `0-1` (same UUID, approved) and only refreshes id and key [inf, as §6.5].
- NHI: OUTMAIL `0x800003f0` -> `0x800003f5` across s2idle, back to `0x800003f0` across
  S3 (power-on value); INMAIL_CMD 0 after both; FW_STS `0x800001a1` [obs] `S3b-M:*`.
  As in every run, OUTMAIL showed `0x800013f0` for one sample at the final unplug.

### 10.3 Model change

The model on `tb3-alpine-ridge` did the opposite across S3 (GUEST-EXITS.md, "S3 and the
PCIe tunnel"; link-retrain memory: "ICM does not rebuild the tunnel; pciehp turns the
slot off"): the tunnel went down at the wakeup reset and the router was re-announced
unapproved, so the NVMe was lost. The capture shows the firmware keeping an approved
device's tunnel across S3 and s2idle and re-announcing it approved with connection id 0
and boot clear. The model is changed to match (`ICM-PROTOCOL.md` R34): mailbox 0x05
saves the present, approved devices; the next driver ready announces them with
connection id 0 and boot clear; the S3 wakeup reset is no longer a power-on for the
pre-boot window or the USB fallback, and within it the ICM tunnels the saved devices
again, so the tunnel is never seen down and the endpoint is kept. Qtest
`/usb4-icm/save-devices` covers s2idle, S3 after a pre-boot tunnel and after a client
approve, S3 without the save, and a cold reset. Not done: a Linux guest S3 leg on
`tb3-alpine-ridge` with the change (no VM for this task).
