# P14s Gen 1 + ORICO AAGM2-U4: a USB4 device on the Alpine Ridge firmware CM, BIOS matrix and `$PIR`

Status: 2026-10-15. Licence: GPL-2.0-only, like the rest of this repository.

The ThinkPad P14s Gen 1 (Intel JHL6240 Alpine Ridge LP, firmware connection manager)
with the ORICO AAGM2-U4 USB4 NVMe enclosure (ASMedia ASM2464PD device router, SK hynix
Gold P31 inside), in all four combinations of the BIOS options "Thunderbolt BIOS Assist
Mode" and "Support in Pre Boot Environment", under Linux and under Windows 98 (MS-DOS
mode). It answers the open Windows 98 `$PIR` question and shows how the firmware treats
a USB4 (not Thunderbolt 3) device. The same enclosure on a USB4 host with a software
CM is [ORICO-ASM2464.md](ORICO-ASM2464.md).

Every statement is **[obs]** (seen in the capture, citation follows) unless tagged
**[inf]** (what the observations imply but do not show). Linux `drivers/thunderbolt`
was used for behaviour only.

## 1. Windows 98 `$PIR`: decode and the open question

### 1.1 The table

All eight runs [obs] `W98:*`: `$PIR` at `F000:CB80`, version 1.0, checksum valid,
interrupt router 00:1f.0 (compatible router `8086:0284`, Comet Lake PCH-LP LPC),
exclusive-IRQ bitmap 0, miniport 0. INT 1Ah `B10Eh` returns the same entries (size =
table size minus the 32-byte header) and dedicated-PCI-IRQ bitmap 0.

Every link field uses only the four values `60`-`63` (PIRQA-D), every IRQ bitmap is
`0xDC78` (IRQ 3, 4, 5, 6, 10, 11, 12, 14, 15). The **table is built at POST** and its
size follows what exists then: `0xC0` (10 entries) with the controller powered down,
`0x110`-`0x120` (15-16) with it present, `0x140`-`0x150` (18-19) with the ORICO tunnelled.

Entries (bus:dev, INTA-INTD links, slot number; `--` = no link). "Always" = in all eight
runs; otherwise the runs that have it:

| Entry | INTA | INTB | INTC | INTD | Slot | Present in | What it is |
|---|---|---|---|---|---|---|---|
| 00:02 | 60 | -- | -- | -- | 0 | always | iGPU |
| 00:04 | 60 | -- | -- | -- | 0 | always | thermal |
| 00:14 | 60 | 61 | 62 | 63 | 0 | always | PCH xHCI, Wi-Fi |
| 00:16 | 60 | 61 | 62 | 63 | 0 | always | ME |
| **00:1c** | **60** | **61** | **62** | **63** | 0 | **always** | root ports 1c.0 (card reader) and **1c.4 (Thunderbolt)** |
| 02:00 | 60 | 61 | 62 | 63 | 33 | always | card reader behind 1c.0 |
| 03:00 | 60 | 61 | 62 | 63 | 10 | controller present | TB switch upstream port (behind 1c.4) |
| 00:1d | 60 | 61 | 62 | 63 | 0 | always | root ports 1d.0, 1d.4 |
| 2d:00 | 60 | 61 | 62 | 63 | 0 | always | Quadro P520 |
| 00:1f | 60 | 61 | 62 | 63 | 0 | always | LPC, audio, SMBus |
| 04:00 | 60 | 61 | 62 | 63 | 4 | controller present | DSP to the NHI |
| 05:00 | 60 | 61 | 62 | 63 | 5 | A0P0_*, A0P1_*, A1P0_OR, A1P1_OR | NHI bus |
| **04:01** | **61** | **62** | **63** | **60** | 4 | controller present | **tunnel DSP** |
| 06:00, 07:00, 08:00 | 61 | 62 | 63 | 60 | 6, 7, 8 | A0P1_OR, A1P1_OR | ORICO switch USP, DSP, NVMe |
| 04:02 | 62 | 63 | 60 | 61 | 4 | controller present | DSP to the TB xHCI |
| 2b:00 | 62 | 63 | 60 | 61 | 43 | A0P*_* only | TB xHCI bus |
| 2e:00 | 61 | 62 | 63 | 60 | 46 | always | internal SK hynix NVMe behind 1d.4 |

Not listed although they have an interrupt pin: 00:08.0 (GMM) and 00:12.0 (thermal).
Slot numbers are not meaningful (mostly the bus number).

Properties [obs], checked entry by entry:

- On bus 0 every device uses `60, 61, 62, 63` for INTA-INTD without per-slot rotation
  (the PCH routes per device).
- Every entry below bus 0 equals the **standard PCI bridge swizzle** up to the bus-0
  entry: 03:00 (device 0 behind 00:1c) = 00:1c; 04:01 (device 1 on bus 4) = 03:00
  rotated by one (INTA -> 61); 04:02 rotated by two; 06:00, 07:00, 08:00 (device 0
  below 04:01) = 04:01. The table is the swizzle written out, not independent wiring.
- A secondary bus gets an entry if it was populated at POST. A1P0_OR shows the edge: its
  table has 05:00 (the NHI bus) but no 2b:00, while the config dump taken later shows the
  NHI gone and the xHCI on 2b present but unconfigured (§3.3). So the BIOS saw the NHI,
  not the xHCI, when it built the table.

Interrupt Line values written by the BIOS (all runs, all devices with an entry) give the
link routing [obs]: **PIRQA (60) = IRQ 11, PIRQB (61) = IRQ 10, PIRQC (62) = IRQ 11**;
no present device uses PIRQD. So the NHI (05:00, INTA, link 60) is on IRQ 11, the TB
xHCI (2b:00, link 62) on IRQ 11, the tunnel DSP and everything behind it (04:01, 06-08,
link 61) on **IRQ 10**. The PCH's PIRQ route registers are not in LPC config space on
this chipset (bytes `0x60`-`0x6b` of 00:1f.0 read 0).

### 1.2 Answer: does the real BIOS cover hot-added tunnel devices?

**Yes.** The table always has an entry for bus 0 device `0x1c` with all four pins, even
with the controller powered down (A1P0_NO, A1P1_NO), and an entry for the tunnel DSP
04:01 whenever the controller existed at POST [obs]. A device that appears behind
04:01.0 after POST (a tunnel your CM brings up) has no entry of its own, so Windows 98
must swizzle [inf, Windows 98's algorithm is not visible in a DOS capture]. Both possible
lookups give the same answer, because the table is a consistent swizzle:

- stopping at the first listed parent: NVMe 08:00 INTA -> 07:00 -> 06:00 -> 04:01 INTA
  = link 61;
- going to bus 0: ... -> 04:01 (device 1) INTA -> 03:00 INTB -> 00:1c INTB = link 61.

Link 61 is IRQ 10 as the BIOS left it. The emulator experiment that motivated the
question (`WIN98-TEST.md`: the hot-added NVMe got Code 29 with the root bridge at 00:1c
because SeaBIOS lists no slot `0x1c`) therefore does not happen on the real P14s, and
`ROOT_ADDR=6` reproduces the real outcome: a bus-0 entry exists above the tunnel.

### 1.3 SeaBIOS versus the P14s, and what the emulator should do

| | SeaBIOS rel-1.17.0, i440FX (`WIN98-TEST.md`) | P14s Gen 1 |
|---|---|---|
| Built | static, compiled in | at POST, from the devices present |
| Router | 00:01.0, `8086:122e` (PIIX3) | 00:1f.0, `8086:0284` |
| Entries | bus 0 devices 1-6 only | every bus-0 device with a routed pin (two exceptions) plus one per populated secondary bus |
| Links | 60-63 rotated per slot (QEMU's i440FX wiring) | 60-63 unrotated on bus 0; swizzled below |
| IRQ bitmap | `0xDEF8` (adds 7 and 9) | `0xDC78` |
| Hot-added device behind a root bridge at `0x1c` | no bus-0 entry, Code 29 | covered (§1.2) |

Recommendation:

1. **Keep `ROOT_ADDR=6`** as the default. It gives the tunnel a bus-0 entry exactly as
   the P14s does; the only visible differences are the PnP location of the root bridge
   (00:06.0 instead of 00:1c.4) and the IRQ numbers, neither of which an xhci98 driver
   should depend on.
2. Do **not** copy the P14s link values into a QEMU table: on i440FX the hardware
   routing is QEMU's per-slot rotation, so a faithful `$PIR` for the emulator must keep
   SeaBIOS's rotated links and only add entries. Copying `60, 61, 62, 63` unrotated would
   route interrupts to the wrong IRQ.
3. If a P14s-shaped table is wanted (root bridge at `0x1c`, entries for the secondary
   buses present at POST), the clean way is a **small SeaBIOS patch** that builds `$PIR`
   after PCI enumeration: one entry per populated bus-0 slot with QEMU's rotation, plus
   one entry per bridge secondary bus with the swizzled links, and the P14s's
   `0xDC78`-style bitmap left as SeaBIOS's. Ship it as a project `bios.bin` selected by a
   `run-win98.sh` option (`PIR=dynamic`, with `ROOT_ADDR=0x1c`). SeaBIOS has no fw_cfg
   input for `$PIR`, and writing a table into the F segment from an option ROM races the
   BIOS's own table and its read-only lock; neither is recommended. Priority low: it
   only matters for testing a driver against the exact P14s bus layout.

## 2. What the firmware does at power-on: the Assist / pre-boot matrix with a USB4 device

### 2.1 Summary

| | Pre-boot off | Pre-boot on |
|---|---|---|
| **Assist off** | NHI and TB xHCI present. No tunnel. The ORICO comes up as a **USB 3.2 Gen 2 UAS disk on the TB xHCI** before the OS (R1-D:1.51, `usb 4-1` on 2b:00.0, "ASM246X series"). Linux's first driver-ready (R1-D:1.548-1.680) announces no device | NHI and TB xHCI present, **tunnel built before the OS** (Win98 sees 06:00/07:00/08:00, A0P1_OR), NVMe probed at R2-D:1.60, announced with `boot` = 1 (R2-S1:`sys-bus-thunderbolt/0-1/boot`), 2 lanes x 20 Gb/s |
| **Assist on** | **NHI hidden**, TB xHCI present but without resources (Win98 A1P0_OR: command 0, BARs 0, line `0xff`, its DSP 04:02 window closed; Linux R3-D:1.148 "init 0000:2b:00.0 fail, -16", BAR "can't assign; no space"). No Thunderbolt and no usable USB path: the ORICO is unusable to both OSes | NHI present, TB xHCI hidden, **tunnel built before the OS** (A1P1_OR, R4), announced with `boot` = 1, **1 lane** x 20 Gb/s (R4-S1, event flags §4.1) |
| Nothing attached | Assist off: NHI and xHCI present (A0P0_NO, A0P1_NO). Assist on: controller powered down, 1c.4 link down (A1P0_NO, A1P1_NO) | same |

With nothing attached the picture equals the 2026-10-14 dock matrix
(`tests/captures/p14s-gen1/README.md`). With a device attached, the dock (a Thunderbolt 3
device) and the ORICO (USB4) differ in two cells:

| Cell | TS3 Plus dock (2026-10-14) | ORICO (2026-10-15) |
|---|---|---|
| Assist off, pre-boot off | no tunnel; dock waits for the OS driver's approval | no tunnel; the ORICO is a USB disk on the TB xHCI |
| Assist on, pre-boot off | **NHI present**, xHCI hidden, dock waits for approval | **NHI hidden**, xHCI present but unconfigured |

### 2.2 Why: a USB4 device falls back to USB when nobody approves it [obs + inf]

R1 shows the mechanism directly. After the replug at the plug prompt:

| Time (trace) | Event | Ref |
|---|---|---|
| 151.727 | device connected, approved = 0, `boot` = 0, connection id 0 | R1-T:151.727 |
| 151.727-151.736 | get route, route 1 | R1-T:151.727 |
| (dmesg 151.668) | Linux registers 0-1 "ASMedia 246x"; boltd does not know the device, nobody approves | R1-D:151.668 |
| 161.112 | **device disconnected** (link 1 depth 1), 9.385 s after the connect, without an unplug | R1-T:161.112, R1-D:161.026 |
| dmesg 161.956 | the ORICO enumerates as a SuperSpeed Plus USB device on bus 4 (TB xHCI 2b:00.0), UAS disk `sda` | R1-D:161.956-162.987 |

So the ASM2464 gives up on the Thunderbolt link about 9.4 s after it is announced
without a PCIe tunnel, and reconnects in USB mode, which the Alpine Ridge routes to its
own xHCI [inf: the cause of the disconnect, ASM2464 or firmware, is not visible; its
timing is]. The disconnect is reported to the OS like a physical unplug.

At power-on the same happens before any OS runs whenever pre-boot is off, which
explains both pre-boot-off cells [inf, consistent with every observation]:

- Assist off: R1 boots with the ORICO already on USB (`usb 4-1` at 1.51 s, before the
  NHI driver started) and the first driver-ready announces nothing.
- Assist on: at POST the BIOS still saw the NHI (it gave 04:00 a memory window and put
  05:00 in `$PIR`, A1P0_OR); when the ORICO fell back to USB the firmware hid the NHI and
  exposed its xHCI, which the BIOS had already left without resources. With Assist on the
  firmware shows the function that matches what is attached: the NHI for a Thunderbolt
  link (dock, `ON_OFF` 2026-10-14), the xHCI for a USB link (ORICO, A1P0_OR), nothing when
  nothing is attached. In R3 the NHI stayed hidden through every unplug and replug
  (no Thunderbolt traffic at all, R3 `watch/` empty) and the TB bridges were removed
  after the last unplug (R3-D:129.19, "Unable to change power state from D3hot to D0").

### 2.3 Pre-boot does not need the boot ACL [obs, with one ordering assumption]

At the end of R1 the boot ACL held only the dock and one other device (last boot-ACL
read, R1-T, `0xa0211100 0x003d0efc 0x28f88500 0x8086d8df`, 14 empty). R2 was the next
boot (no other OS ran in between, and only an OS ICM client writes the ACL): the
firmware tunnelled the ORICO before the OS anyway (`boot` = 1, NVMe at 1.60 s). boltd
then stored the device at 12:35:14 and added it to the ACL (first read in R2-T already
lists `0x70912700 0x174c608e`). So at security level `user`, "Support in Pre Boot
Environment" connects any attached device, not only those in the boot ACL. This settles
the open point of `ICM-PROTOCOL.md` §12.1 against the model's R25 rule (ACL-only).

### 2.4 Event `boot` bit after a hot plug

R2's replug (pre-boot on, Assist off) was announced with approved = 0 **and boot = 1**
(`0x0c110210`, R2-T:130.710): the boot bit is not limited to devices connected at
power-on. Linux keeps `boot` = 1 in sysfs (R2-S5).

### 3.1 R4 timing [obs]

| Time | Event | Ref |
|---|---|---|
| 110.876 (dmesg 110.792) | device disconnected (first unplug) | R4-T:110.876 |
| 109.25-121.27 | NHI registers sampled every 1 s, all normal: firmware status `0x800001a1`, outbound `0x800003f0`, interrupt enable `0x1001` | R4-W:109.246-121.269 |

| later | the replug at the plug prompt did not bring the controller back; no NHI for the rest of the run | `capture.log` "NHIs now:" empty |

Power-off came **10.4-11.4 s after the departure**, OS-visible removal 15.4 s after it.
No ICM command was sent between departure and power-off, so whether the firmware would
have answered in those 11 s is still not captured.

### 3.2 Compared with the dock (2026-10-14 Assist-on run)

The dock run sent boot-ACL reads at +13.8, +19.3, +24.4, +29.5 s, all unanswered, and
the controller was removed at +35.1 s. In that run the platform's bus check at +15.9 s
(dmesg 112.5) removed only the dock's PCI devices and left the switch and the NHI, so
the controller was still powered then [inf: a powered-off controller is removed as a
whole, as at R4-D:126.2]. Together:

- with the dock, the ICM was silent at +13.8 s while the controller was still powered
  (R32 as written holds), and power-off came at most 35 s after the departure;
- with the ORICO, power-off came after about 11 s.

The delay differs by device or by run; the model's single `power-off-delay-ms=35000`
fits the dock. The ORICO value is a reason to test clients with a short delay too.

### 3.3 Why `icm-probe.tsv` is missing in R4 (tool, not hardware)

The tool probed the firmware CM (`boot_acl` reads) only during the tail after the
*last* unplug, and wrote a line only when a domain existed. In R4 the controller
vanished 15 s after the *first* unplug, about 60 s before the tail started, so the probe
loop found no domain, wrote nothing, and the file was never created. Fixed in
`tools/p14s-capture/linux/capture-linux.sh` (2026-10-15): the probe also runs every 2 s
during every unplug prompt and writes "no domain" lines. In R1 and R2 (Assist off) the
tail probe shows every read answered in 30-40 ms (the first in R1 took 1.8 s, a runtime
resume from D3cold).

## 4. The ORICO through the Alpine Ridge ICM, compared with the Framework

### 4.1 Device-connected event [obs] R2-T:81.411, R1-T:151.727, R4-T:87.362

61 words like the dock's, with these differences:

| Field | TS3 Plus dock | ORICO, Assist off | ORICO, Assist on + pre-boot |
|---|---|---|---|
| Header flags | `0xb1`: dual lane, 20 Gb/s, level field 2, bit 0 | **`0xa8`**: dual lane, 20 Gb/s, level field **1**, bit 0 clear | **`0x88`**: 20 Gb/s, **single lane**, level 1 |
| Words 1-2 (UUID bytes 0-7) | `0xa0211100 0x003d0efc` = DROM UID bits 31:0, 63:32 | `0x70912700 0x174c608e` = router UID bits **63:32, 31:0** (ROUTER_CS_8, then ROUTER_CS_7) | same |
| Word 5 at boot (R2, R4) | | `0x0d110110`: key `0x10`, id 1, link 1, depth 1, approved, boot, bit 27 | same |
| Name block | "CalDigit, Inc.", "TS3 Plus", type `0x10` `3d 00 11 00 11 01`, type `0x12` (empty) | "ASMedia", "246x", type `0x10` **`b8 00 63 24 11 02`** (vendor `0x00b8`, model `0x2463`, `0x11`, flags `0x02`: RTD3 bit 0 clear, bit 1 set), **no type `0x12`** | same |

So the firmware synthesises the Intel vendor entry for a non-Intel USB4 router from its
DROM vendor and device IDs, and builds the UUID from the USB4 router UID registers in
high-dword-first order, the opposite of the dock's DROM-derived order. The consequence
is visible in sysfs and boltd: the same enclosure is
`00279170-8e60-4c17-ffff-ffffffffffff` behind the P14s (R2-S1 `unique_id`) and
`8e604c17-0027-9170-ffff-ffffffffffff` behind the Framework's software CM, two different
stored devices for boltd.

### 4.3 What the Linux client reads and writes on the USB4 router through the ICM [obs] R2

Enumeration after the event is fast: 85 requests to route 1 in 13 ms (R2-T:81.567-
81.580), against 400 ms for the dock (whose DROM is read by EEPROM bit-bang). Linux
identifies it as "USB4 Switch: 174c:2463 (Revision: 0, TB Version: 32)", generation 4,
and reads the DROM with the USB4 **DROM Read router operation**: writes to ROUTER_CS_25
(metadata) and ROUTER_CS_26 (opcode `0x24`, operation valid), polling ROUTER_CS_26. It
also issues NVM Sector Size (opcode `0x25`), which completes with status 2, as on the
Framework (`ORICO-ASM2464.md`). Per enumeration: 3 DROM Read and 3 NVM Sector Size
operations. The firmware forwards these writes; this extends `ICM-PROTOCOL.md` §5, which
said the client only writes the EEPROM control dword and the DMA-port mailbox (true for
TB3 routers). Router header as read: `0x2463174c 0x001101c0 0x00000001 0x80000000
0x200000fe` (Notification Timeout 254 ms, set by the firmware; the router's reset value
is 10 ms, `ORICO-ASM2464.md` §1). No link, TMU, CL-state or path access by
the client, as with the dock.

### 4.4 Versus the Framework

| | P14s, Alpine Ridge firmware CM | Framework, Linux software CM |

| Who enumerates and tunnels | firmware; OS only approves | Linux |
| At boot with the device attached | tunnel kept from pre-boot (pre-boot on), else USB mode | firmware tunnel, then Linux's host reset ("0: resetting") drops and rebuilds it |
| Link | 2 x 20 Gb/s (1 lane under Assist on + pre-boot) | 2 x 20 Gb/s |

## 5. MD-2: endpoint reset evidence on the P14s path [obs] R2

- Physical unplug and replug (R2-D:104.86 link down, 130.76 link up): both ASM2464
  bridges come back with bus numbers 0 ("bridge configuration invalid ([bus 00-00])",
  R2-D:130.888, 130.890), Command 0 ("enabling device (0000 -> 0003)" for both bridges,
  "(0000 -> 0002)" for the NVMe, R2-D:130.892-130.895), NVMe BARs unassigned; the nvme
  driver probes a new controller. Same signature as the Framework (`ORICO-ASM2464.md`
  §11): a reset endpoint after every link loss.
- Pre-boot tunnel into the OS: no reset. The NVMe is probed at R2-D:1.60 with the BIOS's
  resources (no "enabling device" line); the firmware CM has no host-router reset, so
  unlike the Framework the tunnel is not dropped at boot.
- Driver unbind and rebind (R2 ~77-81 s): no PCIe event at all; the tunnel and the
  endpoint survive, as with the dock (R22).

## 6. Windows 98 view per configuration

Device presence and `$PIR`: §1, §2.1, and the table in the capture README. Further
[obs]:

- **Interrupt lines** (BIOS): NHI 11 (link 60), TB xHCI 11 (link 62, when configured),
  tunnel DSP 04:01 and the ORICO's switch and NVMe 10 (link 61), root port 1c.4 and the
  15c0 ports 11 except 04:01 (10).
- **NHI under DOS**: command `0x0002` (memory decode, no bus master), MSI and MSI-X off,
  INTA, BAR0 `E0100000` (Assist off) or `E0000000` (Assist on), as with the dock.
- **NHI registers under DOS** (`PCIDUMPN.TXT`, only A1P1_OR could be read): host
  capabilities `0x0000000c`, DMA misc **`0x01000012`**, inbound command `0x00000000`,
  outbound **`0x800003f0`**, firmware status `0x800001a1`. So the firmware runs in
  connection-manager mode (3) before any driver, with the Intel auto-clear bit (DMA misc
  bit 2) clear and no mailbox command issued yet. In the other runs PCIDUMP 1.1 refused
  the read ("A20 off and no XMS") because BAR0 `E0100000` has address bit 20 set and the
  XMS local A20 enable failed on this machine (HIMEM loaded, "high memory area is not
  available"); PCIDUMP 1.2 falls back to a wrap test.
- **ORICO tree under DOS** (A0P1_OR, A1P1_OR): 06:00.0 and 07:00.0 `1b21:2463` with
  command `0x0007`, buses 06-07-08, NVMe 08:00.0 `1c5c:174a` with BAR0 `D4100004` (Assist
  off) or `D4000004` (Assist on), command `0x0007`: fully configured by the BIOS, usable
  by a DOS or Windows 98 NVMe driver without any Thunderbolt driver.
- **`ENUM.REG`** is byte-identical in all eight runs: it is the registry of the last
  Windows GUI session, exported from DOS, so it records no per-configuration state. It
  holds the NHI as "PCI System Peripheral" with ConfigFlags `0x40` (no driver), the TB
  xHCI and the 15c0 ports, and no ASMedia `1b21:2463` entry (the GUI never saw the ORICO
  tunnelled). The IRQs Windows 98 itself assigned are not in it (they live in
  `HKEY_DYN_DATA`).

## 7. Register values and timing that differ from the 2026-10-14 runs [obs]

- **Outbound mailbox** reads `0x800003f0` at power-on and through binds, unbinds and
  rebinds (R1-R4 `mmio/*-1-initial` to `-3-after-rebind`, W98:A1P1_OR); it became
  `0x800003f5` only after the NHI's first runtime suspend to D3 (R1-W:145.874). The
  2026-10-14 runs showed `0x800003f5` because the NHI had already runtime-suspended
  before the first dump. One sample read `0x800013f5` (bit 12 set) for under a second
  (R1-W:306.150).
- **Driver-ready response** under Assist on: `0x01002203 0x28010b60` (R4-T:86.764):
  flags `0x22`, i.e. RTD3 (bit 6) **and bit 7 clear**; Assist off: `0x0100e203` as
  before (R1, R2). This confirms the indirect inference of `CAPTURE-VS-LINUX.md` AR-27.
- **First driver-ready after power-on**, dmesg time from "starting RX ring 0" to
  "security level set to user" (the client's host-router poll succeeds after the
  firmware has announced the attached devices): R1 0.13 s (nothing announced), R2 0.80 s
  (pre-boot ORICO), **R4 2.77 s** (Assist on, pre-boot ORICO). After a rebind it is about
  0.6 s in R2 and R4 (event at R4-T:87.362, 0.60 s after driver-ready).
- The rebind reset the NHI's `power/control` to `auto` (R1 `pci/tb-complex-with-device/
  0000_05_00.0/sysfs-attrs.txt`), so R1's NHI runtime-suspended despite the tool's
  "keep in D0" setting; fixed in the tool (`reassert_d0`).

## 8. Implications for the model (follow-up items)

Ordered by value for xhci98. Status 2026-10-15 (QEMU branch `usb4-p14s`, in main as of `b5936c4`):
items 1-8 and 10 are implemented ([ICM-PROTOCOL.md](../ICM-PROTOCOL.md) R2, R8, R10,
R11, R25, R30, R32, R33; results in §13.7 there); item 9 stays as recommended (no
SeaBIOS change). QEMU branch `usb4-orico2` (in main as of `36f6254`) adds the UAS side of
item 1 and the ASM2464's captured PCIe link registers (2.5 GT/s x1 upstream; §13.7
there).

1. **USB fallback of an unapproved USB4 device (§2.2).** On `tb3-alpine-ridge`, a USB4
   device router (e.g. `device-model=asm2464`) not approved within about 9.4 s of its
   announcement should leave the Thunderbolt side (device-disconnected event) and, if
   the TB xHCI is modelled, appear on it as a USB 3 device. At power-on with pre-boot off
   this has already happened before the guest runs. An xhci98 ICM client must approve
   within that window or expect the device on the xHCI instead.
2. **Pre-boot without the ACL (§2.3).** R25 approves only boot-ACL devices; the real
   firmware tunnelled a device not in the ACL. Make pre-boot approve every attached
   device at security level `user` (keep the ACL rule behind an option if wanted).
3. **Assist on + pre-boot off + USB4 device (§2.1):** NHI hidden, TB xHCI present
   without resources, nothing usable. Needs item 1's USB mode; until then document it
   as unmodelled in `PLATFORM-MATRIX.md`.
4. **Event content for a USB4 device behind Alpine Ridge (§4.1):** flags `0xa8` (and
   `0x88`, single lane, under Assist on + pre-boot); UUID words = (UID high, UID low);
   name block vendor/model from the DROM, vendor entry `(vid, did, 0x11, 0x02)`, no type
   `0x12` entry. Today `usb4-icm.c` sends `0xb1`, the DROM-UID order and always the
   `0x12` entry, which match the TB3 dock only.
5. **Router operations through the ICM (§4.3):** verify that `tb3-alpine-ridge` with an
   `asm2464` device forwards ROUTER_CS_25/26 writes and DROM Read / NVM Sector Size
   (R31 only drops path-space and PCIe-adapter Path Enable writes, so it should).
6. **Driver-ready flags under Assist on (§7):** `0x22`, not `0xe2` with bit 6 cleared.
7. **Reset values (§6, §7):** outbound mailbox `0x800003f0` and DMA misc `0x01000012` at
   power-on (R2 currently specifies `0x800003f5` and `0x01000016`); the low nibble `5`
   after the first D3 and bit 2 only once a client sets it.
8. **Assist power-off delay (§3):** about 11 s with the ORICO (35 s is the dock's upper
   bound); offer an ORICO-like value in the run scripts or note it next to
   `power-off-delay-ms`.
9. **`$PIR` (§1.3):** keep `ROOT_ADDR=6`; optional dynamic-`$PIR` SeaBIOS build for a
   P14s-shaped bus layout.
10. Lower: single-lane link under Assist on + pre-boot; first-driver-ready delay of 2.8 s
    under Assist on; the ASM2464 upstream link at 2.5 GT/s x1 (modelled for both hosts,
    in main as of QEMU `36f6254`).
